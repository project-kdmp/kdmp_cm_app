# 2.1.2 (203)

2026-09-28 · 기준 버전 2.1.1(202)

2.1.1 까지가 콜을 띄우는 길을 놓은 것이라면, 2.1.2 는 **그 길에서 손님이 막히던
자리를 걷어낸다.** 도착지를 지울 수 있고, 운행 화면에서 나올 수 있고, 카드가
등록되고, 주소는 치는 동안 따라오고, 조회가 실패하면 실패했다고 말한다.

## 스토어 제출용 (Play Console 붙여넣기)

Play Console 의 "이 버전의 새로운 기능" 은 **언어당 500자 제한**이다. 아래는 464자다.

```
[호출]
· 주소를 치는 동안 결과가 바로 따라옵니다. 검색 버튼을 누르지 않아도 됩니다.
· 도착지를 지우는 X 버튼과 경유지 추가가 생겼습니다.
· 집·회사를 자주 가는 주소로 저장해 한 번에 넣습니다.
· 요금을 휠로 굴려 고르거나 직접 입력할 수 있습니다.

[운행]
· 접수·배차·운행·완료 4단계로 지금 어디까지 왔는지 보입니다.
· 운행 중 내 이동 위치를 지도로 볼 수 있습니다.
· 운행 화면에서 뒤로 나갈 수 있고, 홈의 배너로 다시 들어갑니다.

[개선]
```

## 상세

### 호출 — 막히던 자리들

| 내용 | 커밋 |
|---|---|
| 주소를 치는 동안 결과가 따라온다 | `4a8e812` |
| 도착지 초기화 · 경유지 추가 · 자주 가는 주소 칩 | `d1a4491` |
| 요금을 휠로 고르고 직접 입력한다 | `ee7d113` |
| 지도 라벨 탭이 죽어 있던 문제 | `dfd7d76` |

**주소 검색.** 검색 키를 눌러야 결과가 나왔다. 주소는 한 번에 맞게 치기 어렵다 —
「서울역」인지 「서울역로」인지, 「역삼동」인지 「역삼로」인지. 치고 누르고 아니면
지우고 다시 치는 일을 반복해야 했다.

그냥 `onChanged` 로 부르면 안 되는 것이 셋 있었다. 글자마다 부르면 주소 API 를 몇
배로 두드리므로 손이 멈춘 뒤 **400ms** 에 한 번만 부른다. 한 글자로는 주소를 좁힐
수 없어 **두 글자**부터 찾고, 그 사이에는 최근 검색 기록을 그대로 둔다 — 안 그러면
한 글자 쳤을 때 기록도 결과도 없어 화면이 통째로 빈다. 자동 검색은 요청이 겹치므로
요청할 때의 검색어를 기억해두고 그 사이 바뀌었으면 응답을 버린다. 「강남」 결과가
「강남대로」보다 늦게 도착해 목록에 섞이는 일을 막는다.

**도착지·경유지.** 도착지를 지울 수단이 없어 다른 곳으로 바꾸는 것만 가능했다.
`endMapData` 만 비우면 `_getDrivingCalculate()` 가 즉시 반환해 요금이 남으므로
경유지·거리·요금을 함께 정리하는 `clearEndMapData()` 를 따로 뒀다. 경유지는 표시와
삭제만 되고 추가할 수단이 아예 없었다 — 백엔드는 이미 `stopOverList` 를 받으므로
앞단만 붙였다.

자주 가는 주소는 서버 보관 API 가 없어 단말에만 저장한다. 집·회사 두 자리만 지원한다.

**요금.** `-`/`+` 버튼만 있었고 한 번에 1,000원이었다. 2만 원을 올리려면 스무 번
눌러야 했으니 큰 금액을 넣을 길이 사실상 없었다. 가운데를 휠로 바꿔 1,000원 눈금에
스냅시키고, 눈금이 넘어갈 때 햅틱을 준다. 버튼은 남겨 휠을 움직이게 했다.

휠은 1,000원 눈금만 짚을 수 있어 그 사이 금액은 가운데를 눌러 직접 친다. 모드를
오가는 버튼은 두지 않았다 — 키보드가 내려가면 그대로 휠로 돌아온다. 직접 친 금액을
가까운 눈금으로 끌어다 붙이지 않고 **눈금 자체를 그 금액에 맞춰 다시 잡는다.**
23,500 을 치고 빠져나왔을 뿐인데 24,000 이 되어 있으면 값이 제멋대로 바뀐 것으로
읽힌다.

부수 효과로 요금이 0 인 상태가 사라졌다. 운행 중 요금 올리기는 최소값이 「현재
요금 + 1,000」이라 **열자마자 올릴 수 있는 가장 낮은 금액이 잡힌다** — 전처럼 `+`
를 한 번 눌러야 확인이 켜지지 않는다.

**지도 라벨.** 마커에는 탭 리스너가 있었는데 그 위에 뜨는 「출발지 변경」
인포윈도우에는 없었다. 그렇게 써 놓고 글씨를 누르면 아무 일도 일어나지 않았으니
눌러야 할 곳을 잘못 알려준 셈이다. 글씨는 작은 마커보다 크고 눈에 먼저 띈다.

### 운행 — 어디까지 왔는지, 어디로 가는지

| 내용 | 커밋 |
|---|---|
| 콜 진행 4단계 표시와 종료 후 리뷰 · 정산 복구 | `219cb6f` |
| 운행 화면에서 나갈 수 있게 하고 홈에서 다시 들어간다 | `39111c1` |
| 운행 중 이동 경로를 접힌 지도로 본다 | `9857a9e` |
| 기사가 배차를 확정하면 예약 정보가 바로 갱신된다 | `02dba44` |

**4단계 표시.** 운행 화면이 `CAL` 인지 아닌지로만 갈려 기사 확정(`CCO`) · 출발지
대기(`WAT`) · 운행 시작(`STA`)이 화면상 완전히 같았다. 손님은 기사가 오는 중인지
이미 타고 가는 중인지 알 수 없었다. 상태 코드 14개를 접수 · 배차 · 운행 · 완료
4단계로 접어 상단에 표시한다.

**리뷰 · 정산 복구.** 운행종료 후 리뷰와 정산이 뜨지 않았다. 가는 길이 FCM 푸시
하나뿐이었는데 세 군데서 끊겼다 — 앱이 꺼진 상태로 받은 푸시는 스트림에 넣지
않았고, 백그라운드 수신분은 별도 isolate 라 UI 스트림에 닿을 수 없고, 운행 화면이
떠 있지 않으면 broadcast 스트림이라 버려졌다. 복구 경로도 없어서 손님 폰이 주머니에
있는 동안 기사가 종료하는 실제 상황에서는 거의 항상 실패하는 구조였다. 조회한
상태가 `END`·`REN` 이면 푸시와 무관하게 리뷰를 띄운다.

**뒤로가기.** 운행 화면에서 소프트키 뒤로가기가 막혀 있었다. 진짜 이유는 화면이
막은 것이 아니라 **홈이 운행 중이면 자동으로 다시 들여보냈기 때문이다** — 나가도
곧바로 돌아왔다. 자동 진입을 배너로 바꿨다. 운행 중이면 홈에 「운행 중 · 이어보기」
배너가 떠서 손님이 직접 눌러 들어간다.

**이동 지도.** 운행 중 내 위치를 볼 수 있게 접힌 카드를 뒀다. 기사 위치가 아니라
손님 자신의 이동 경로다. 펼치지 않으면 위치 구독을 걸지 않는다(`distanceFilter` 20).
`STA`·`RST` 에서만 노출한다.

접었다 펼칠 때 해제된 네이티브 뷰를 건드려 `MissingPluginException: clearOverlays`
가 나던 것을 컨트롤러 null 처리와 `mounted` 확인으로 막았다.

**배차 확정 즉시 반영.** 예약 정보를 보고 있는데 기사가 확정해도 화면이 그대로였다.
푸시만으로 갱신한다 — `initState` 에서 구독하고 `RCO`·`CCO` 가 오면 다시 읽는다.
`StreamBuilder` 안에서 푸시를 처리하면 무한 루프가 되므로(기사앱에서 같은 문제로
다이얼로그가 72회 떴다) 구독을 `initState` 로 옮겼다.

### 이용내역

| 내용 | 커밋 |
|---|---|
| 취소된 콜도 목록에 남긴다 | `e7cea48` |
| 예약 건이 접수 시각을 예약 일시로 보여주던 문제 | `9b7b2e8` |
| 예약 · 운행 건에 접수 일시를 함께 보여준다 | `eb79b4b` |

예약 정보 화면의 일시가 기사 앱과 달랐다. 기사 앱은 `drvReserveDt` 를 쓰는데 고객
앱은 운행 전이라 `drvStartDt` 가 없으면 `reqRegDt` 로 떨어지고 있었다. 9/19 에 넣은
9/20 예약이 고객에게는 9/19 로 보였다.

라벨이 「일시」 하나였던 것이 문제의 절반이다. 값과 라벨을 함께 정하도록 바꿨다 —
운행 시작 후는 운행 일시, 예약 접수 후 운행 전은 예약 일시, 그 외는 접수 일시.

그런데 일시 한 줄이 상태에 따라 갈리므로 예약·운행 건을 열면 **언제 접수했는지 볼
길이 없어졌다.** 예약·운행을 가리킬 때만 접수 일시를 한 줄 더 붙인다. 접수 시각만
있는 건은 같은 값을 두 줄로 보여줄 이유가 없으니 비워 둔다.

취소 건은 삭제 버튼을 감춘다. 내역 숨김(`cm_show_yn`)은 `kdmp_drv_end` 에만 있는
컬럼이라 취소에는 걸리지 않아, 눌러도 지워지지 않고 완료 문구만 떴다.

### 결제

| 내용 | 커밋 |
|---|---|
| 카드 등록 본인확인이 항상 실패하던 문제 | `6fe1375` |
| 카드가 없을 때 인디케이터가 렌더링 예외를 내던 문제 | `a7be5da` |

가입은 SMS 소유 확인만 하고 CI 를 받지 못해 `ci_test_휴대폰뒷4자리` 임시값을
저장한다. 그런데 카드 등록의 본인확인은 모빌리언스가 발급한 실제 CI 와 이 값을
비교하고 있었다. 둘이 같을 수 없으므로 **스테이징 · 운영 가릴 것 없이 카드 등록이
100% 막혀 있었다.**

저장된 값이 실제 CI 가 아니면 대조할 기준이 없는 것이므로, 이번 인증에서 받은 실제
CI 를 기준값으로 저장하고 통과시킨다. 그 다음 등록부터는 대조가 동작한다.

> 서버에 회원 CI 를 갱신하는 API 가 생기면 기기와 무관하게 대조할 수 있다.
> 그때까지는 **첫 등록에서 명의 일치를 보장하지 못한다.**

카드 목록이 비면 `PageView` 도 비어 컨트롤러의 `offset` 이 NaN 이 되는데,
`SmoothPageIndicator` 의 페인터가 그 값을 `floor()` 하면서 터졌다. 카드 등록 직후
목록을 다시 읽는 순간 빈 상태를 지나며 재현된다.

### 공통 — 조회 상태와 팝업

| 내용 | 커밋 |
|---|---|
| 조회 상태를 화면이 말하게 한다 (AsyncView) | `6963399` |
| 바텀시트 하단이 소프트키에 가리던 문제 | `3f03869` |

화면들이 로딩과 실패를 다루지 않고 있었다. 실측하면 `is Loading` 을 보는 화면이
하나뿐이고 `is Fail`·`is Bad` 를 보는 화면은 **없었다.** 뷰모델은 상태를 만들어
두는데 받는 쪽이 없어, 조회가 느리거나 실패하면 빈 화면이 그대로 남았다. 고객은
세 가지를 구분할 수 없었다 — 불러오는 중인가, 기록이 없는가, 실패했는가. 느린
망에서는 기록이 있는데도 「이용내역이 없습니다」로 읽혔다.

`AsyncView` 로 네 갈래를 나눈다. 실패에는 사유와 함께 다시 시도할 자리를 준다 —
할 수 있는 일이 없으면 안내가 안내로 기능하지 않는다. 이미 보여줄 것이 있으면
로딩·실패여도 본문을 유지한다. 그러지 않으면 다음 쪽을 불러오는 중에 목록이 통째로
사라진다.

이용내역 목록 한 곳에 먼저 적용했다. 나머지 화면은 이 화면에서 쓸 만한지 보고
넓힌다.

바텀시트 7곳의 하단 여백을 `viewInsets.bottom + padding.bottom` 으로 맞췄다.
리뷰 작성 팝업의 버튼이 소프트키에 가려 누를 수 없던 것이 시작이었다.

## 확인하지 못한 것

기기 확인은 **debug 빌드로 했고, debug 는 STAGE 를 바라본다**
(`main.dart:123` — `kDebugMode ? STAGE : PROD`). 릴리스는 PROD 다. 코드와 서버
스키마는 양쪽이 같으므로 다르게 보일 이유는 없지만, 운영 데이터로 눌러본 것은 아니다.

`AsyncView` 의 **실패 화면은 실기기에서 재현해보지 못했다** — 비행기 모드로 조회를
실패시키는 확인이 남아 있다. 로딩 · 빈 상태는 확인했다.
